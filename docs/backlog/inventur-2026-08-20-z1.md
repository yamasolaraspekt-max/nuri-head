## K-1 · Kausalität · `insulationType` wird gelesen, aber nirgends gesetzt

**beleg:** Lesestelle `projection/raumProjektion.ts:91` (`… insulationType ? 'aussenwand_gedaemmt' : 'wand'`);
Modell `domain/scene.types.ts:109`, Zod `domain/validation.ts:46`; einziger construction-Regler
`app/rahmen/EigenschaftenPanel.tsx:324` schreibt nur `materialId`. `grep -rn insulationType` →
genau 3 Treffer (Typ, Schema, Lesestelle), **keine Schreibstelle im ganzen Baum**.
**beschreibung/erklaerung:** Jede Wand projiziert konstant `'wand'`, egal welche Materialwahl der
Nutzer trifft; der Zweig `aussenwand_gedaemmt` ist toter Code — VOR der PHP-Grenze, verschieden
vom bekannten `bauteil_typ`-PHP-Befund (anderes Kettenglied).
**erledigt_wenn:** UI-Regler setzt das Feld, ODER Zweig ehrlich als unverdrahtet ausgewiesen
(Muster „ehrlich null" wie `decke`/`boden` ebd. :95-96).
**loesungsvorschlag:** Checkbox/Select „gedämmt" neben dem Mauerwerk-Select. **aufwand:** S

## K-2 · Kausalität · Dach-Traufhöhe friert bei Erzeugung ein

**beleg:** Setzstelle nur `app/HausplanerApp.tsx:1007` (`traufhoeheMm: level.elevation +
level.defaultWallHeight`, einmalig bei Dach-Erzeugung); Wandhöhen-Änderung
`EigenschaftenPanel.tsx:336` → `applyCommand.ts:208-228` (`UPDATE_NODE`, keine Nebenwirkung auf
Dächer); Wandmesh folgt (`segmentierung.ts:60`), Dachmesh nicht (`dachMesh.ts:89` liest nur das
eingefrorene Feld). `UPDATE_LEVEL` ebenso ohne Dach-Nebenwirkung (`applyCommand.ts:380-393`).
**erklaerung:** Nach Wandhöhen-Änderung laufen Wand und Dach visuell auseinander, ohne Hinweis.
**erledigt_wenn:** Höhenänderung aktualisiert `traufhoeheMm` betroffener Dächer ODER expliziter
Hinweis/Sperre. **loesungsvorschlag:** Nebeneffekt in `applyCommand.ts` analog
`passeOeffnungenEin` (:222), oder `traufhoeheMm` als abgeleiteten Wert führen. **aufwand:** M

## K-4 · Kausalität · DIN-18065-Badge prüft die Durchgangshöhe nie

**beleg:** Engine führt Kopfhöhe als Fehler-Kriterium (`treppenBerechnung.ts:97-99`,
`DURCHGANG_MIN=2000` :58) — aber nur `if (e.durchgangshoehe !== undefined)`. Reale Aufrufe ohne
das Feld: `EigenschaftenPanel.tsx:494`, `szene.ts:406-412` (via `treppe3D.ts:44-50`). Badge
„DIN 18065 erfüllt" `EigenschaftenPanel.tsx:499`. Demo-Rechner bietet das Feld an
(`enginePanels.ts:141`, Vorgabe 2000) — Demo und echte Treppe liefern bei gleichen Eingaben
verschiedene Urteile.
**erklaerung:** `bestanden` kann für eine platzierte Treppe NIE an der Kopffreiheit scheitern —
auch unter einer Dachschräge nicht; das Badge suggeriert Vollprüfung.
**erledigt_wenn:** Kopfhöhe hergeleitet und durchgereicht ODER Badge benennt die Lücke.
**loesungsvorschlag:** Sofort: Text „(ohne Durchgangshöhen-Prüfung)"; dann Herleitung aus
Geschosshöhe/Deckenunterkante. **aufwand:** S (Text) / M (Herleitung)

## P-1 · Plausibilität · Walmdach-Fläche bis +75 % zu groß bei Giebelbreite > Firstlänge

**beleg:** `geometry/dachGeometrie.ts:134-146` (`case 'walm'`): `firstLenM = max(0, laengeM−spannM)`
klemmt still auf 0, Walm-Dreieck bleibt auf voller Giebelbreite. Gegenrechnung gegen das
Projektions-Theorem (Σ Facetten = Grundriss/cos α): Fall 6×8 m, 30° → gerechnet 64,66 m² statt
55,43 m² (**+16,6 %**); Fall 4×10 m → 80,83 statt 46,19 m² (**+75 %**), Fehler wächst unbegrenzt.
Live-Pfad: `HausplanerApp.tsx:1024` + `dachProjektion.ts:29` — laut Kopf „die belastbare Quelle
für PV/Heizlast". **Die passende Prüfung existiert bereits:** `dachformVorlagen.ts:414-416`
`walmIstKonsistent` (getestet), läuft aber nur im Vorlagen-Preview, nie im Live-Pfad; und
`walmFirstlaengeM` (:336-341) dokumentiert ausdrücklich „wird NICHT still auf 0 geklemmt" — genau
das tut `dachGeometrie.ts:136`.
**erledigt_wenn:** Für `spannM > laengeM` Ausnahme `DachGeometrieUngueltig` ODER Fläche erfüllt
Kontrollrechnung ±1 % — nachgewiesen an beiden gerechneten Fällen.
**loesungsvorschlag:** Konsistenzprüfung in `dachFlaechen()` einziehen (Muster :88-93).
**⚠ YAMA-POSTEN (Produktentscheidung):** ablehnen (Nutzer legt First anders) oder First
automatisch auf die längere Achse drehen? **aufwand:** S
